# 修改后验证

## 执行步骤

### 1. 定位变更范围
- 通过 `git diff` 或最近编辑记录，列出本次所有被修改的文件。
- 对每处修改，标注：文件路径、修改类型（新增/删除/修改）、影响行数。

### 2. 语法与基础检查
- 检查修改后的文件是否有语法错误（如括号不匹配、引号未闭合、缩进错误）。
- 检查导入/依赖是否完整（如是否引用了未定义的变量、删除了仍被使用的导入）。
- 检查类型一致性（如 TypeScript 类型是否匹配、函数签名是否一致）。

### 3. 逻辑正确性检查
- 逐行对比修改前后，确认逻辑意图是否被正确实现。
- 检查边界条件：空值、越界、异常情况是否被处理。
- 检查控制流：if/else、循环、return 路径是否完整且正确。
- 检查异步逻辑：async/await、Promise、回调是否正确配对。

### 4. 影响面检查（最重要）
- **调用方检查**：如果修改了函数签名/接口，检查所有调用处是否同步更新。
- **全局搜索**：对修改的函数名、变量名、常量名做全局搜索，确认无遗漏。
- **副作用检查**：修改是否影响了其他模块？是否破坏了原有行为？
- **配置检查**：是否涉及环境变量、配置文件、路由、数据库 schema 的变更？

### 5. 测试验证
- 如果项目有测试，运行与修改相关的测试用例：`npm test` 或针对性测试。
- 如果修改了测试文件本身，确认测试断言是否正确。
- 如果无自动化测试，提供手动验证建议（如关键功能点、边界场景）。

### 6. 输出验证报告

```text
## 变更概览
- 修改文件：X 个
- 主要变更：...

## 检查结果

### 通过项
- ...

### 警告项（需关注）
- ...

### 问题项（必须修复）
- ...

## 建议
- ...
```

## 禁止事项
- 不要只看修改的那几行，必须检查调用方和依赖关系。
- 不要假设"应该没问题"，必须逐一验证。
- 不要忽略类型错误和 lint 警告。
- 不要跳过测试步骤（如有测试）。
